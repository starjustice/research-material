1 · Old bridge vs New Architecture — JSI

Say this: "The bridge was async and JSON-serialized, so scroll events queued up under load. JSI lets JS call native code directly and synchronously — that's the concrete reason the New Architecture is faster, not just marketing."

2 · Release process — store path vs OTA path

Say this: "Anything native has to go through a build and a store review, which can take days. A pure JS fix can ship over the air in minutes — but OTA can never touch native code, that's the hard limit."

3 · FlatList — render only the visible window

Say this: "FlatList only keeps a small window of real native views on screen and recycles them as you scroll — same idea as react-window on web, just built in by default here."

One snippet to remember: a resilient FlatList configuration. Expand to FlashList verbally for the heavy-list case.

<FlatList
  data={items}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <Row item={item} />}
  getItemLayout={(_, i) => ({
    length: ROW_HEIGHT, offset: ROW_HEIGHT * i, index: i,
  })}
  initialNumToRender={10}
  windowSize={5}
  removeClippedSubviews
/>
How to talk about it: "keyExtractor gives each row a stable identity for recycling — same idea as React's key. getItemLayout skips a measurement pass because I know every row's height up front, which also makes scrollToIndex instant instead of estimated. For anything heavier — a feed, a chat, a catalog — I'd reach for FlashList v2 instead, which auto-measures items and is built for the New Architecture."
