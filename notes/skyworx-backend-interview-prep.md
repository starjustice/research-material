## 2. Opening walkthrough (prepare 2–3 minutes, they will ask for this)

Structure the opening by the layers of the request, not by soal number:

1. **"Request masuk lewat middleware dulu"** — ExceptionHandlingMiddleware catches everything and returns clean JSON (never a stack trace), then Serilog request logging records method, path, status, duration.
2. **"Auth pakai JWT"** — `/api/auth/login` issues an HMAC-SHA256 token (issuer, audience, lifetime all validated). All kredit endpoints have `[Authorize]`.
3. **"Validation di DTO"** — data annotations (`[Range]`) + `[ApiController]` returns automatic 400 before the controller runs. Plafon/tenor must be > 0, bunga 0–100 (exactly what the soal asked).
4. **"CRUD lewat EF Core ke PostgreSQL"** — DTOs are separate from the entity, UUID primary key, `created_at`/`updated_at`, indexes on plafon and tenor (in the EF migration *and* visible in the DB backup).
5. **"Angsuran pakai rumus anuitas"** — constant monthly payment; unit-tested against the exact example in the PDF (Rp100jt, 12%, 60 bulan → Rp2.224.444,77).
6. **"Tests pakai xUnit"** — isolated in-memory database per test so tests run in parallel safely.

## 3. Likely questions per soal — with answers based on MY actual code

### Soal 1 — Database & indexing

**Q: Why UUID as primary key instead of auto-increment?**
- The spec required UUID. But defend it: UUIDs can be generated by the app before insert (no round trip), safe to expose in URLs (no guessing `/1`, `/2` — enumeration attack), and merge-friendly across environments.
- Honest tradeoff: random UUIDs write to random index pages (worse locality than serial). At their scale that's fine; if it ever mattered, UUIDv7 (time-ordered, supported natively in Postgres 18, and by generators before that) fixes it. Knowing UUIDv7 exists is a senior signal.

**Q: Your two indexes — when do they actually help? (likely probing question)**
- `ix_pengajuan_kredit_plafon` and `ix_pengajuan_kredit_tenor` are separate B-tree indexes. They help queries that filter or sort on **one** of those columns.
- **Be ready for the trap:** my query `ORDER BY tenor DESC, plafon DESC LIMIT 1` is *not* fully served by two separate indexes. Postgres can scan the tenor index backward, but the tie-break on plafon isn't in that index. A **composite index** `(tenor DESC, plafon DESC)` would serve the whole query with a single index scan + LIMIT 1.
- Say it before they do: *"Kalau query ini jadi hot path, saya akan buat composite index (tenor, plafon) — dua index terpisah tidak optimal untuk ORDER BY dua kolom."* Then mention you'd verify with `EXPLAIN ANALYZE` — always measure, never guess.

**Q: Explain your SQL answers.**
- Longest tenor + highest plafon: `ORDER BY tenor DESC, plafon DESC LIMIT 1` — my interpretation: longest tenor first, plafon as tie-breaker. Acknowledge the other reading (two separate queries: MAX tenor, MAX plafon) and say you'd clarify the business intent first — that's what a senior does with ambiguous requirements.
- Average: `SELECT AVG(bunga) FROM pengajuan_kredit` — simple aggregate; index doesn't help a full-table AVG.

### Soal 2 — CRUD API, JWT, validation

**Q: Walk me through what happens when a request hits `POST /api/pengajuankredit`.**
- Middleware order (this is the answer they want): exception handler → Serilog request logging → HTTPS redirection → **authentication** (validates JWT signature/expiry/issuer/audience, fills `HttpContext.User`) → **authorization** (`[Authorize]` check) → model binding + validation (automatic 400 with field errors) → controller action → EF Core `SaveChangesAsync` → 201 Created with `CreatedAtAction` pointing at the GET-by-id route.

**Q: Your login is hardcoded admin/admin123. Why?**
- Deliberate, and the code comment says so: the spec had no user table or registration flow, so I kept scope tight and documented the boundary.
- Then show you know the real version: Users table, passwords hashed with **BCrypt or Argon2** (never plain, never reversible encryption), login checks hash, short-lived access token + **refresh token** for renewal, roles in claims for authorization. *"Kalau ini production, login-nya validasi ke tabel Users dengan password BCrypt, dan saya tambah refresh token."*

**Q: Your JWT secret is in appsettings.json. Is that safe?**
- No — own it immediately: fine for a local assessment, wrong for production. Production: environment variables or a secret manager (Azure Key Vault / AWS Secrets Manager) — *and I wrote exactly that in my Soal 7 CI/CD answer*, so point them to it. Consistency between code and written answers looks good.
- Bonus: mention key rotation and that HMAC (symmetric) could become RSA (asymmetric) if other services need to verify tokens without holding the signing key — that connects to the microservice/gateway answer.

**Q: Why DTOs separate from the entity?**
- The entity is the database shape; the DTO is the API contract. Separating them means: clients can't set fields they shouldn't (`Id`, `CreatedAt` — mass-assignment protection), validation lives on the input model, and the DB schema can change without breaking the API contract. Same reason I use input types in GraphQL.

**Q: (The big one) Your Create endpoint accepts `Angsuran` from the client. Should it?**
- **Best answer: no — and I'd change it.** Angsuran is *derived* from plafon + bunga + tenor. Accepting it from the client means the client can send an inconsistent value (plafon 100jt but angsuran Rp5.000) — in a real loan system that's a data-integrity bug with money attached.
- The fix: compute angsuran server-side in the Create/Update path (reuse the Soal 3 formula — one source of truth), or at minimum validate that the submitted value matches the computed one.
- Why it's like this: the soal defined the table with an `angsuran` column and CRUD on that table, so I followed the spec literally. Saying "here's what I'd harden for production" **proactively** turns this from a weakness into your best senior moment. Lead with this one.

**Q: GetAll returns every row. What happens with 1 million pengajuan?**
- Own it: `ToListAsync()` with no pagination was fine for the assessment, wrong at scale — it loads the whole table into memory per request.
- The fix, concretely: `?page=&pageSize=` with `.OrderBy(x => x.CreatedAt).Skip((page-1)*pageSize).Take(pageSize)`, return total count + items; for very large data, keyset/cursor pagination (`WHERE created_at < @cursor ORDER BY created_at DESC LIMIT @n`) because OFFSET gets slower the deeper you page. I also wrote pagination in my Soal 6 answer — consistent story.

**Q: What if two users update the same pengajuan at the same time?**
- Current code: last write wins. For a loan system I'd add **optimistic concurrency**: a `xmin`/rowversion token in EF Core; the UPDATE fails with `DbUpdateConcurrencyException` if the row changed since it was read, and the client gets 409 Conflict. (Connects to my DBO double-refund war story if they want a real example of why concurrency control matters.)

### Soal 3 — Angsuran calculation

**Q: Explain the formula.**
- Annuity (PMT) formula — fixed monthly payment on a reducing balance: `angsuran = (P × i) / (1 − (1 + i)^−n)` where `i` = monthly rate (annual bunga / 100 / 12), `n` = tenor in months.
- Walk the PDF example: P = 100.000.000, bunga 12%/year → i = 0,01, n = 60 → 1.000.000 / (1 − 1,01⁻⁶⁰) = 1.000.000 / 0,44955 ≈ **Rp2.224.444,77**. My unit test asserts exactly this.
- Contrast with **flat interest** (bunga flat: plafon × bunga × tahun / bulan, common in Indonesian multifinance) — knowing both exist and asking which one the business uses is domain awareness Skyworx will love.

**Q: You cast decimal to double for the math. Why — isn't double dangerous for money?**
- Honest answer: `Math.Pow` doesn't exist for `decimal`, so the exponent forces floating point. Double has ~15–17 significant digits; for realistic plafon/tenor values the error is far below 1 rupiah, and I round to 2 decimals at the end.
- The stricter production version: compute the power with `decimal` in a loop (or a decimal-pow helper), round with a defined policy (`MidpointRounding` — banker's rounding vs away-from-zero matters in finance and should be a business decision), and unit-test boundary cases. Naming `MidpointRounding` = senior signal.

**Q: What about bunga = 0?**
- Edge case: formula divides by `1 − (1+0)^−n = 0` → division by zero (double gives Infinity, not an exception!). Correct behavior: bunga 0 → angsuran = plafon / tenor. My validation allows bunga = 0 (Range 0–100), so this is a real gap — **mention it proactively** as "the edge case I'd fix": guard clause + test.

### Soal 4 — Unit testing

**Q: Why xUnit, and how are the tests isolated?**
- xUnit is the current .NET default (used by the ASP.NET team). Each test creates its own **in-memory EF Core database with a unique GUID name**, so tests share nothing and run in parallel safely.

**Q: What do your tests NOT cover? (they may probe honesty)**
- Calling controller methods directly skips the HTTP pipeline — so `[Authorize]`, `[Range]` validation, and model binding **are not exercised** (validation runs in the pipeline, not in the method). Also the InMemory provider isn't real Postgres — no real SQL, no index behavior, case-sensitivity differs.
- The upgrade path: **integration tests with `WebApplicationFactory`** (spin up the real pipeline in-memory, send real HTTP requests, assert 401 without token / 400 for bunga = 150), and **Testcontainers** to run tests against a real disposable PostgreSQL. Naming these two tools is the expected senior answer in .NET.

### Soal 5 — Error handling & logging

**Q: How does your error handling work?**
- Three layers: validation errors → automatic 400 with field messages ([ApiController]); not-found → explicit 404 with a clean message; everything unexpected → ExceptionHandlingMiddleware catches, logs with full stack via Serilog, returns a generic 500 JSON (never leaks internals to the client).
- Middleware ordering rationale: exception handler is registered **first** so it wraps everything after it, including the request logger.

**Q: What about logging request/response bodies? PII?**
- Current: Serilog request logging = method, path, status, duration (+ file sink with daily rolling). Bodies are *not* logged — and for a finance company that's half-right by accident: say it deliberately. If body logging is needed for audit, mask PII fields (no full KTP numbers, no salaries in plain logs) and cap body size. In production add correlation/request IDs propagated in headers so one pengajuan can be traced across services, and ship logs to something searchable (Seq / ELK / CloudWatch) instead of only files.

### Soal 6 & 7 — expect follow-ups on my written answers

My answers were solid (cache-aside with TTL + invalidation on write, service split auth/pengajuan/angsuran, DB per service, gateway with rate limiting, rolling deploys, backward-compatible migrations, secrets in a vault, PR discipline, prod debugging with logs → reproduce → rollback if urgent). Likely follow-ups:

- **"Redis: what about cache stampede / stale data?"** — TTL for tolerable staleness, delete-on-write for correctness-sensitive keys (I wrote this); add: request coalescing/lock for stampedes, and never cache per-user financial state without careful keys.
- **"Your microservice split — why by function?"** — split by operational need and load profile: auth is security-critical, angsuran calculation is CPU-bound and stateless (scales independently), pengajuan is the transactional core. But **lead with the honest disclaimer**: for the actual test scale, one well-structured service is correct; I'd split when load or team size proves it. (This matches the 2025–2026 modular-monolith consensus and my real DBO experience running exactly this architecture — API/auth/cron/queue services with BullMQ on Docker Swarm.)
- **"Traffic spike — walk me through it live"** — my written runbook: metrics first (CPU/memory/connections) → scale up/out → pagination/filters on heavy endpoints → cache hot reads → rate limit (tighter if it smells like bots) → communicate to stakeholders. Add one number: connection pool exhaustion is usually the first thing that breaks — pooling (PgBouncer / EF pooling) before anything exotic.
- **"Production-only bug"** — check environment differences first (env vars, config, data), read logs around the failure (mask PII), reproduce in staging with production-like data, bisect recent deploys; if users are bleeding, roll back first and debug in parallel. Have ONE story ready: my TADA double-refund incident — duplicate webhooks, race condition, row locking + idempotency fix — it's a perfect production-bug story for a finance company.

## 4. Weaknesses to own PROACTIVELY (say them before they ask)

Order by impact — each one framed as "what I'd harden for production":

1. **Angsuran should be computed server-side, not accepted from the client** (data integrity — the #1 thing to say).
2. **Bunga = 0 breaks the annuity formula** (division by zero → Infinity) — needs a guard + plafon/tenor fallback + test.
3. **No pagination on GetAll** — page/pageSize now, keyset later.
4. **Hardcoded login** → Users table + BCrypt + refresh tokens.
5. **JWT secret in appsettings** → env vars / Key Vault (already in my written answer).
6. **No integration tests** → WebApplicationFactory + Testcontainers.
7. **No rate limiting** — .NET 8 has built-in `AddRateLimiter` middleware; one paragraph to add it.
8. **No concurrency token** on update → optimistic concurrency, 409 on conflict.

Saying 3–4 of these unprompted is the strongest senior signal available in this meeting: it shows you know the difference between "passes the test" and "production for a bank."

## 5. C# / .NET questions they may ask (since my background is JS/TS)

They know my daily stack is Node/TypeScript. Expect "do you actually understand .NET?" questions. The mapping that keeps answers grounded:

| .NET concept | What I say + JS/TS anchor |
|---|---|
| **Middleware pipeline** | Same mental model as Express middleware; order matters; `app.Use...` ≈ `app.use()`. I ordered exception → logging → auth deliberately |
| **Dependency injection** | Built-in container; constructor injection everywhere. Lifetimes: **Singleton** (one instance forever), **Scoped** (one per request — `AddDbContext` default, so each request gets its own DbContext/unit-of-work), **Transient** (new every resolve) |
| **async/await + Task** | Same concept as Promises; `Task` ≈ `Promise`. Difference worth naming: C# async is thread-pool based, not single-event-loop — but the "don't block" rule is the same (`await`, never `.Result`, which can deadlock) |
| **EF Core vs Prisma** | Same role: schema-as-code + migrations + typed queries. EF: `DbContext` tracks changes, `SaveChangesAsync` flushes; LINQ ≈ Prisma query builder; `Include` ≈ Prisma `include` |
| **LINQ** | `Where/Select/OrderBy` ≈ `filter/map/sort`, but translated to SQL when used on `IQueryable` |
| **decimal vs double** | `decimal` = base-10, exact for money (like Prisma Decimal / no JS native equivalent — a real advantage of C#); `double` = IEEE float. I used decimal in the entity, double only inside the pow calculation |
| **Nullable reference types** | Compile-time null safety ≈ TS `strictNullChecks`; `entity is null` pattern matching in my controllers |
| **Records / DTO classes** | DTO classes with data annotations ≈ zod/class-validator on input types |

Honest framing if asked directly: *"Sehari-hari saya di Node/TypeScript, tapi konsepnya sama — DI, middleware, ORM, async. Yang saya pelajari khusus untuk test ini: EF Core migrations, data annotations, dan Serilog — dan menurut saya hasilnya idiomatic .NET, bukan Node yang ditulis pakai C#."*
