IaaS → PaaS → SaaS → FaaS, and serverless in depth.

Draw these on the whiteboard. Practice each in under 30 seconds.

1 · The "who manages what" ladder

Say this: "It's a ladder of who manages what. IaaS I own the OS up; PaaS I push code; SaaS I just log in; FaaS I ship one function. My CapRover-on-a-VPS is IaaS with a self-hosted PaaS layer on top."

2 · FaaS anatomy — trigger, instance, response

Say this: "A function is triggered by an event — a request, a queue message, an S3 upload, or a timer. It runs, returns, and dies. It keeps no memory between calls, so I never store sessions or files in it."

3 · The Postgres connection explosion (and the fix)

Say this: "Each function instance opens its own DB connection, so a spike exhausts Postgres. I put a pooler — PgBouncer or RDS Proxy — in front, or use a serverless driver like Neon's. Same reason I pool connections in my container setup, just more urgent."

4 · Image-resize (event-driven serverless job)

Say this: "Upload lands in S3, the upload event triggers a Lambda that resizes and writes to a second bucket. No always-on worker — it runs only when an image arrives. In my DBO system I'd do this with a BullMQ worker instead; the tradeoff is I pay for that worker even when idle."

5 · Isolate vs container startup (why Workers have no cold start)

Say this: "Lambda boots a mini-machine per instance, so the first request waits. Workers use V8 isolates — starting one is like opening a browser tab, so cold starts basically disappear."

The serverless handler shape: one function per event, no persistent process.

// One handler per event. Nothing stays alive between requests.
export async function POST(req: Request): Promise<Response> {
  const body = await req.json();
  // Keep business logic provider-agnostic (portable, avoids lock-in):
  await handleWebhook(body);        // dedupe on idempotency key inside
  return new Response("ok", { status: 200 }); // answer fast, enqueue heavy work
}
How to talk about it: "The handler is a thin wrapper around plain functions — that keeps me portable and dodges vendor lock-in. For the database I'd front Postgres with a pooler (RDS Proxy / PgBouncer) or a serverless driver (Neon), because each instance opens its own connection. Heavy work goes on a queue so I return 200 fast."
