1 · The classic scalable web architecture

Say this: "The app tier is stateless — sessions live in JWT or Redis — so I can scale horizontally behind the load balancer. Reads that tolerate lag go to the replica."

2 · Cache-aside (the caching pattern to know)

Say this: "Cache-aside with a TTL. Risks: stale data — I delete on write for correctness-sensitive keys — and cache-miss stampedes, fixed with request coalescing."

3 · Queue + worker (async work done right)

Say this: "At-least-once delivery means duplicates happen, so workers are idempotent — I dedupe on an idempotency key. Failed jobs retry with backoff, then land in a dead-letter queue."

4 · The Postgres scaling ladder (climb in order, stop early)

Say this: "Most 'we need to shard' conversations end at step 1. A tuned single Postgres handles ~100GB and thousands of QPS."

5 · Fan-out: on write vs on read

Say this: "Hybrid wins: push for normal users, pull for high-follower accounts, merge at read time. That's how Twitter/Instagram handle celebrity skew."

One snippet to remember: Redis fixed-window rate limiter. Expand to token bucket verbally.

async function allow(userId: string, limit = 100): Promise<boolean> {
  // per-minute window
  const key = `rl:${userId}:${Math.floor(Date.now() / 60_000)}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, 60);
  return count <= limit; // false → respond 429 + Retry-After
}
How to talk about it: "This is fixed-window — simple but allows a 2× burst at the window edge. In production I'd use a token bucket (allows short bursts, enforces average rate) or sliding window, and run it in Redis so it works across all instances behind the load balancer."
