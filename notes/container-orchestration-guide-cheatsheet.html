Draw these on a whiteboard. Each should take under 40 seconds.

1 · The ladder you are already on

Say this: "Compose is many containers on one machine. Swarm is many machines with self-healing and rolling deploys — that is what CapRover runs under the hood, so I already operate an orchestrator. Kubernetes is the same job with a declarative API, autoscaling, and policy, at a much higher operational cost."

2 · Cluster anatomy and the path of one request

Say this: "Request path: DNS to a cloud load balancer, into the ingress controller pods, which apply host and path rules and hand off to a Service. The Service is a stable name in front of pods that keep changing. The control plane never touches a request — it only decides what runs where and keeps reality matching the spec."

3 · Declarative — the reconciliation loop

Say this: "The mental shift from docker run is declarative. I do not issue commands that happen once. I record the end state and a control loop keeps reality matching it forever. That is why the same file applied twice changes nothing, and why infrastructure can live in Git."

4 · Rolling update with maxSurge 1 and maxUnavailable 0

Say this: "maxSurge 1 means one extra pod may exist; maxUnavailable 0 means I never drop below full capacity. A new pod only receives traffic after its readiness probe passes, and an old pod leaves the Service endpoint list before it is stopped, so in-flight requests finish. Rollback is instant because the old ReplicaSet is still there."

5 · Liveness vs readiness — different failures, different actions

Say this: "Liveness means restart me — so it checks only the process. Readiness means stop sending me traffic — so it checks dependencies like Postgres and Redis. Putting the database check in liveness is the classic mistake: one database blip restarts every pod simultaneously."

The ~16 commands worth knowing. The debugging order at the bottom is what interviewers listen for.

CommandWhat it doesWhen you reach for it
kubectl get pods -o widewhat is runningAdds the NODE and IP columns. First command of every debugging session.
kubectl get pods -wwatch changes liveDuring a rollout or while testing self-healing.
kubectl describe pod <name>why it is not workingThe Events list at the bottom explains Pending, ImagePullBackOff, and probe failures.
kubectl logs <pod> -fstream logsNormal log reading. Add -c <container> for multi-container pods.
kubectl logs <pod> --previouslogs of the dead containerThe one command people forget. Essential for CrashLoopBackOff.
kubectl exec -it <pod> -- shshell insideCheck env vars, DNS, mounted files. Read-only debugging, never fixes.
kubectl apply -f ./k8sdeclare desired stateThe normal way to deploy. Idempotent — running it twice changes nothing.
kubectl diff -f ./k8spreview the changeShows what apply would do. Good habit before touching production.
kubectl rollout status deploy/apiis the deploy done?Exits non-zero on failure, so CI pipelines use it as the gate.
kubectl rollout undo deploy/apirollbackSeconds, because the previous ReplicaSet still exists.
kubectl rollout restart deploy/apirestart all podsAfter a ConfigMap or Secret change — those do not restart pods by themselves.
kubectl scale deploy/api --replicas=5manual scaleQuick capacity change. Gets overwritten by the next apply — put it in the file.
kubectl port-forward svc/api 8080:80reach it from your laptopWorks with no ingress and no public IP. Your everyday debugging tunnel.
kubectl get events --sort-by=.lastTimestampwhat just happenedCluster-level view: evictions, scheduling failures, OOM kills.
kubectl top podslive CPU and memoryRight-sizing requests and limits. Needs metrics-server installed.
kubectl get all -n <ns>everything in a namespaceOrientation in an unfamiliar cluster.
Debugging order to say out loud: get pods (what state?) → describe pod (events explain Pending / ImagePull / probe failure) → logs --previous (why it crashed) → get events (cluster-level cause) → top (resource pressure).

Exit codes: 137 = OOMKilled, memory limit exceeded. 1 = the app threw on startup. 143 = stopped by SIGTERM, which is normal during a rollout. 
# The five lines that make a Deployment production-grade
strategy: { type: RollingUpdate, rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
readinessProbe: { httpGet: { path: /ready, port: 3000 } }   # checks DB + Redis
livenessProbe:  { httpGet: { path: /healthz, port: 3000 } } # process only
resources: { requests: { cpu: 100m, memory: 256Mi }, limits: { memory: 512Mi } }
terminationGracePeriodSeconds: 30   # + handle SIGTERM in Express and BullMQ

🗣 How to describe your own experience — honestly

"I run production containers on Docker Swarm through CapRover — a self-hosted PaaS layer over Swarm. I own the deploys: multi-service builds, rolling updates with health checks, env and secret config, nginx routing with Let's Encrypt TLS, and rollbacks. I have not operated a Kubernetes cluster in production. I have run clusters locally with kind and the concepts map closely: my Swarm services are Deployments plus Services, CapRover's nginx is an Ingress, my env vars are ConfigMaps and Secrets, my health check splits into readiness and liveness probes, and my Cron service becomes a CronJob. What I would learn on the job is the operational side — RBAC, upgrades, and storage."

Why this wins: overclaiming Kubernetes is exposed by one follow-up question. Honest framing plus demonstrated concept mastery makes everything else you say believable.
