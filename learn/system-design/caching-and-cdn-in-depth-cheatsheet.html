CACHING & CDN CHEATSHEET

Layers · HTTP headers · Patterns · Invalidation · CDN and Next.js · Failure modes · Redis and Valkey

A cache is a copy that trades freshness for speed. Redraw each picture from memory.

1 · The layers: a request stops at the first fresh copy

Say this: "A cache is a copy closer to the reader. I add it where data is read far more than it changes, and I watch the hit ratio, because the real win is the load it takes off the database."

2 · Cache aside, and delete after commit

Say this: "I use cache aside: the app reads Redis, on a miss reads Postgres and saves a copy with a TTL. On a write I commit, then delete the key. If Redis dies, the app still works, only slower."

3 · The race: a slow reader writes old data back after the delete

Say this: "Delete on write still has a race: a slow reader reads the old row, I commit and delete, then it saves the old row back. A short TTL limits the damage. For data that matters I add a version check or a lease, like Facebook's memcache."

4 · Stampede: one hot key expires

Say this: "When a hot key expires, every request misses together and the database falls over. I let one request reload while the rest wait or get the old value, and I add random jitter to TTLs so keys do not expire together."

5 · CDN: edges, origin shield, origin, signed URLs

Say this: "Public files go through edges near users, with an origin shield so a miss reaches my server once, not once per edge. Private files get a short lived signed URL, so my API checks permission but never streams the bytes."

6 · Redis is down: fail open or fail closed

Say this: "Redis must not be a single point of failure for reads. Short timeouts and a circuit breaker; catalog reads fail open to Postgres with a limit so it survives; a rule like an OTP rate limit fails closed."

Explain each out loud. Tick only when you can.

Cache-Control in plain words

DirectiveMeans
max-age=60Any cache may use it for 60 s without asking
s-maxage=300CDN and proxies only, 300 s. Browsers ignore it
privateOnly the user's browser may keep it, never a CDN
no-cacheKeep it, but ask the server first every time (often a 304)
no-storeDo not keep it anywhere
stale-while-revalidate=30After it goes stale, serve old for 30 s while fetching new
immutableNever changes. For hashed file names like app.3f9a.js

Cache patterns

PatternHowPick whenCost
Cache asideApp reads cache, on miss loads DB, sets with TTLDefaultMiss after change, stale until delete or TTL
Read throughA library loads on missLoading logic in one placeSame as cache aside
Write throughWrite DB, then set cacheData read right after writeSlower writes, cold data in cache
Write behindWrite cache now, DB laterCounters, views, likesData loss if cache dies
Refresh aheadReload before expiryFew hot keys that must never missReloads nobody reads

Failure modes

ProblemWhat happensFix
StampedeHot key expires, all miss togetherSingle flight, Redis lock, serve stale, early refresh
Hot keyOne key melts one Redis nodeLocal 1 to 5 s cache tier, split the key into copies
PenetrationIds that do not exist always reach the DBCache the miss, bloom filter, validate input
AvalancheMany keys expire at the same secondTTL jitter: 3600 + random 0 to 300
Cold startEmpty cache after deploy, flush or purgeWarm top keys, roll out slowly, no purge at peak
Redis downEvery read waits on timeoutsTimeouts, circuit breaker, fail open with a limit

Design round checklist

StepExample: product catalog
1 WhatProduct details, categories. Not stock at checkout
2 WhereCDN for images and public pages, Redis for product JSON
3 PatternCache aside, delete on write
4 Key and TTLshop:v3:product:7:lang-id, 10 min with jitter
5 InvalidationDEL after commit, tag purge on the CDN
6 Failure modeSingle flight, local tier for hot items, fail open with a limit
7 MetricHit ratio, p99, DB queries per second, evictions, memory
