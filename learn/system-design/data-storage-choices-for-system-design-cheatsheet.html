DATA STORAGE CHOICES CHEATSHEET

The storage menu · File uploads · Search · Reports · Copies · Splits · IDs · Data life

Pick storage by the question it answers. Redraw each picture from memory.

1 · The storage menu: one job each

Say this: "I pick storage by the question it must answer. Postgres is the source of truth. Files go to S3, search to a search index, big reports to a column store. Each extra store has one named job."

2 · File upload with a presigned URL

Say this: "The client gets a presigned URL from my API, uploads straight to S3, and an S3 event starts a worker that checks the file and marks it ready in Postgres. A CDN serves reads."

3 · Search: the inverted index

Say this: "A search index is a list from each word to the records that hold it. I start with Postgres full text and a GIN index. If I add OpenSearch, it is a copy fed by an outbox or CDC, and I can rebuild it."

4 · Row store for the app, column store for reports

Say this: "User traffic and reports have different shapes. Reports go to a replica first, then to a column store fed by CDC. Postgres stays fast for users."

5 · Quorum: R + W > N

Say this: "In a leaderless store like Cassandra I pick N, W and R. With N equal to 3, W and R of 2 overlap on at least one node, so reads see the newest write."

6 · Consistent hashing: the ring and virtual nodes

Say this: "With hash mod N, adding one server moves most keys. On a ring, a new server takes only its slice, about one Nth. Virtual nodes give each server many spots, so load stays even."

7 · The life of data: hot, warm, cold, deleted

Say this: "I plan the data's life on day one: hot in Postgres, old partitions archived to S3 as Parquet, deleted after the retention period. For banks I ask about data residency and personal data first."
