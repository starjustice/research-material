ARCHITECTURE PATTERNS 2026 CHEATSHEET

Layers · Modular monolith · Boundaries · Gateway and BFF · Serverless · Events · Tenancy · AI features · ADRs

Split for a reason you can name. Redraw each picture from memory, then say the line under it.

1 · Three shapes: same boxes, different lines

Say this: "I start with a modular monolith: one deploy, strong module walls, each module owning its tables. I pull a module out only for a named reason: its own team, its own deploy speed, its own scale, or failure isolation."

2 · Strangler fig: move one route at a time

Say this: "I never do a big bang rewrite. I put a router in front, move one route or bounded context at a time, watch it in production, and roll back by switching the route."

3 · Gateway for everyone, a BFF per client

Say this: "The gateway does the shared checks: routing, HTTPS, token and rate limits. A BFF, or GraphQL, shapes data per client, so mobile gets small payloads and web gets rich pages."

4 · Three ways to keep customers apart

Say this: "I start with shared tables, tenant_id on every row and Postgres row level security, because it is cheapest to run and migrate. A huge or regulated tenant moves to its own database."

5 · The LLM gateway: one door to every model

Say this: "I treat the model as a slow, costly, sometimes-down third party. It sits behind one gateway with per-tenant budgets, cost logs, timeouts and a fallback provider."

6 · RAG on the Postgres you already have

Say this: "I keep vectors in the same Postgres with pgvector, so the tenant filter and permissions sit next to the data. Retrieval quality matters more than the model, so I test it with evals."

7 · Ports and adapters: the core imports nothing outside

Say this: "The core defines the interfaces it needs, and Prisma, HTTP and email code plug into them. Rules become testable without a database, and vendors stay at the edge. I use it only where there are real rules."

Explain each out loud. Tick ✓ only when you can.
