QUEUES, STREAMS & EVENTS CHEATSHEET

Sync vs async · At least once · Retries and DLQ · Queue vs log vs pub/sub · Lag · Outbox, inbox, sagas

Picture first. Redraw each one from memory, then say the "Say this" line out loud.

1 · Sync vs async: do not make the user wait for slow work

Say this: "If the user is waiting for the answer, I call it directly. If nobody is waiting, I add a job to a queue, answer in milliseconds, and let a worker do it with retries."

2 · Ack and visibility timeout: why a job can run twice

Say this: "A worker can crash after the work and before the ack, so the queue delivers again. Delivery is at least once. Exactly once is at least once plus an idempotent worker."

3 · Retries with backoff and jitter, then the dead letter queue

Say this: "Temporary errors get a few tries with exponential backoff and jitter, so workers do not retry all at once. After the last try the job goes to a dead letter queue, I alert on its size, and I replay after the fix."

4 · Three shapes: work queue, log, pub/sub

Say this: "A work queue hands each job to one worker and deletes it. A log like Kafka keeps events, so many groups read them and I can replay. Pub/sub copies one event to every listener. Order is kept only per key."

5 · Outbox and inbox: no lost events, no double events

Say this: "I save the event in the same transaction as the order, so it can never be lost. The receiver inserts the message id into an inbox table first, so a second copy does nothing."

6 · Lag: the queue grows quietly

Say this: "Queues fail quietly. I alert on the age of the oldest message and consumer lag, and I autoscale workers on queue depth, capped by partitions and by the partner's rate limit."

7 · Orchestrated saga: undo in reverse order

Say this: "Across services there is no shared transaction, so I use a saga: local steps, each with an undo. For money flows I orchestrate it, so one place knows the state and runs the undos in reverse order."
