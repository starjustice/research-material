SQL PATTERNS CHEATSHEET

16 patterns behind most "advanced SQL" questions · name it, write it, index it

Half of the patterns are window functions. Understand this one picture and they all get easy.

1 · GROUP BY collapses rows. A window function keeps them.

2 · Anatomy of OVER ( … )

SUM(delta) OVER (
  PARTITION BY store_id                     -- WHO are my neighbours?  (like GROUP BY, without collapsing)
  ORDER BY created_at, id                   -- in WHAT ORDER?          (needed for running, LAG, ranks)
  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW  -- HOW FAR do I look?  (the frame)
)
Trap: with ORDER BY and no frame, rows with the same sort value are treated as one step, so they show the same running total. Add a tiebreaker (, id) or write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.

4 · The other window functions you need

FunctionGivesPattern
LAG(x) / LEAD(x)value from the previous / next rowmonth over month, time between events
SUM(x) OVER (ORDER BY …)running totalbalance after each ledger row
SUM(x) OVER (PARTITION BY …)group total on every rowpercent of store total
AVG(x) OVER (ROWS n PRECEDING)moving average7-day average
FIRST_VALUE / LAST_VALUEfirst / last in the framefirst order date per store
NTILE(4)bucket number 1–4quartiles of stores by revenue
Order of SQL: FROM → WHERE → GROUP BY → HAVING → SELECT (window functions run here) → ORDER BY → LIMIT. That is why you cannot put a window function in WHERE: wrap it in a subquery or CTE and filter outside.

Traps that cost points

TrapWhat happensFix
LEFT JOIN + WHERE on right tableRows with no match vanish (becomes INNER JOIN).Move the filter into ON.
COUNT(*) after LEFT JOINCounts 1 for a store with no orders.COUNT(o.id) counts only real matches.

Window function in WHEREError: windows run after WHERE.Wrap in a CTE, filter outside.
