1 · Composite index = phone book (the burn topic)

Say this: "Two single-column indexes can never produce a two-column ordering — plafon isn't sorted inside each tenor. One composite index is; and a plain ASC one serves DESC-DESC via a backward scan. I verify with EXPLAIN ANALYZE: the Sort node must be gone."

2 · The slow-query workflow (recite it)

Say this: "I never guess. pg_stat_statements tells me which query, EXPLAIN ANALYZE tells me why, then I index or rewrite, then I run EXPLAIN ANALYZE again to prove it — and I check the new index's write cost."

3 · OFFSET vs keyset pagination

Say this: "OFFSET re-counts the line from the front on every page. Keyset leaves a bookmark — the last row's (created_at, id) — and the index resumes from there. Tradeoff: no jump-to-page-N, which feeds don't need."

4 · FOR UPDATE SKIP LOCKED — job queue in pure Postgres

Say this: "Plain FOR UPDATE makes worker B wait behind worker A's row — serial processing. SKIP LOCKED means take the next open counter. It's how pg-boss and Graphile Worker do queues — the 'BullMQ without Redis' option for moderate volume."

5 · MVCC and VACUUM — why dead tuples exist

Say this: "Postgres is MVCC — readers never block writers because updates write new versions. The price is dead tuples; autovacuum collects them at about 20% dead. The classic production issue is a long transaction silently blocking that cleanup."

One annotated plan, before and after. Read inner-most node first.

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE store_id = 42 ORDER BY created_at DESC LIMIT 10;

-- BEFORE (no useful index):
Limit (cost=2745.94..2745.96 rows=10) (actual time=21.343..21.345 rows=10 loops=1)
  -> Sort (...)                        ← Sort node = index is NOT serving the ORDER BY
       Sort Key: created_at DESC
       Sort Method: top-N heapsort  Memory: 26kB
                                       ← "external merge Disk" here = sort spilled past work_mem
       -> Seq Scan on orders           ← read the WHOLE table
            (cost=0.00..2743.00 rows=101)
            (actual time=0.012..21.201 rows=98 loops=1)
                                       ← estimated 101 vs actual 98 = stats are healthy
            Filter: (store_id = 42)
            Rows Removed by Filter: 99902   ← 99,902 rows of pure waste = missing index
            Buffers: shared hit=1743        ← 1743 pages touched (hit=cache, read=disk)
Execution Time: 21.371 ms

CREATE INDEX idx_orders_store_created ON orders (store_id, created_at);

-- AFTER:
Limit (actual time=0.030..0.056 rows=10 loops=1)
  -> Index Scan Backward using idx_orders_store_created on orders
                                       ← Backward = DESC served by a plain ASC index
       Index Cond: (store_id = 42)
       Buffers: shared hit=13          ← 1743 pages → 13 pages
Execution Time: 0.078 ms              ← 21 ms → 0.08 ms
The 5 things to check, in order: 1. Scan type — Seq Scan filtering to few rows = missing index. Index Only Scan = best case.
2. Sort nodes — a Sort feeding a LIMIT means the index doesn't match the ORDER BY.
3. Estimated vs actual rows — off by 10–100×? Run ANALYZE; stale stats cause bad join choices.
4. Rows Removed by Filter — wasted work, the "why is this slow" number.
5. Buffers — hit = cache, read = disk. Huge counts explain slowness even when the plan looks right. (PG18: shown by default.)
Join algorithms — one line each when they appear: Nested Loop — small outer side, indexed inner side. Fine. Scary only when both sides are big.
Hash Join — builds a hash table on the smaller side; the workhorse for large equality joins.
Merge Join — both inputs sorted (usually via indexes), zipped together; big sorted joins.
Careful: EXPLAIN ANALYZE really runs the query. For UPDATE/DELETE wrap it: BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;
